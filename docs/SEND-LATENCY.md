# Sideglow 0.3.0-preview.3 — 전송이 느릴 때 확인하기

**설정 → 최근 전송 시간…**에서 최근 B 전송 시도 한 건의 시간을 확인할 수 있습니다. 이 화면은 어느 구간이 오래 걸리는지 구분하기 위한 기능입니다. 실제 사용자의 Windows·Discord 환경에서 지연 개선 폭을 측정한 결과는 아직 없습니다.

채팅창의 전송 성공 시간과 AI 대기·완료 시간 상태줄은 기본으로 숨깁니다. 기본 설정의 **채팅창에 지연 시간 표시**를 켜면 다시 볼 수 있습니다. 표시를 꺼도 오류 안내와 **최근 전송 시간…**의 기록은 유지됩니다. AI 번역의 처리 시간은 별도의 [최근 번역 시간 안내](AI-TRANSLATION.md#최근-번역-시간으로-확인하기)를 참고하세요.

## 유지한 전송 동작

Discord가 메시지 저장을 확인하면 **그 서버 응답에 들어 있는 문장**을 바로 표시합니다. 같은 메시지가 Discord PC 앱을 거쳐 다시 수신되기를 추가로 기다리지 않습니다. 메시지 ID와 채널, 본문·작성자·시간이 확인되어야 하며, 전송 버튼을 누른 초안을 미리 성공한 것처럼 표시하지 않습니다. 이미 수신한 수정·삭제를 늦은 전송 응답이 덮어쓰지 않도록 처리합니다.

연결 준비에서 웹후크를 확인한 HTTP 세션은 같은 전송 작업자가 계속 사용합니다. 첫 메시지를 보낼 때 별도의 발신 세션을 새로 준비하던 경로를 줄였습니다. **매번 전송 전에 웹후크의 대상 채널을 확인하는 GET은 유지합니다.** Windows의 시스템·사용자 프록시 설정도 그대로 따릅니다. 따라서 모든 네트워크 지연이 사라지거나 특정 전송 속도가 보장되는 변경은 아닙니다.

`wait=true`는 Discord가 저장을 확인하고 생성된 메시지를 응답하도록 요청하는 옵션입니다. 이를 꺼서 확인 없이 성공 처리하지 않습니다. API의 정확한 의미는 [Discord Webhook 문서](https://docs.discord.com/developers/resources/webhook)에 있습니다.

## 시간을 확인하는 방법

1. 기존 Sideglow를 완전히 종료하고 새 실행 파일을 엽니다. 설정 창 제목에서 **0.3.0-preview.3**을 확인하세요.
2. 평소처럼 메시지를 전송합니다. 기존에 연결되었다면 새 앱이나 웹후크를 만들 필요는 없습니다.
3. 전송 결과가 나온 뒤 Alt+Tab으로 Sideglow를 선택하고 **설정 → 최근 전송 시간…**을 누릅니다. 아직 이번 연결에서 전송 결과를 받은 적이 없으면 버튼이 비활성화되어 있습니다.
4. 시간이 적힌 작은 창을 확인합니다. 최근 한 건만 보관하므로 다른 메시지를 보내면 새 기록으로 바뀝니다. 재실행하거나 연결을 다시 구성하면 초기화됩니다.

## 표시되는 값

1,000 ms는 1초입니다.

| 항목 | 측정하는 구간 |
|---|---|
| **전체** | 전송 큐에 들어간 뒤 UI가 전송 결과 이벤트를 꺼낼 때까지 |
| **대기열** | 앞선 작업이 끝나고 이 메시지의 전송 작업이 시작될 때까지 |
| **웹후크 대상 채널 확인** | 보내려는 웹후크가 선택한 채널을 가리키는지 확인하는 GET |
| **메시지 전송·저장 확인** | 실제 POST를 보내고 Discord의 저장 확인 응답을 해석할 때까지 |
| **UI 이벤트 전달** | 전송 작업자가 결과를 만든 뒤 UI가 그 결과를 꺼낼 때까지 |
| **요청 보내기** | POST의 WinHTTP 보내기 호출. 연결 준비·DNS·TLS·프록시 처리 등이 영향을 줄 수 있음 |
| **Discord 응답 기다리기** | POST 응답과 상태 헤더를 받는 구간. 순수한 Discord 서버 내부 처리 시간만 뜻하지 않음 |
| **응답 본문 읽기** | POST가 반환한 메시지 본문을 읽는 구간 |

마지막 세 항목은 **메시지 전송·저장 확인** 안의 세부 구간입니다. 전체 시간에 다시 더하지 마세요. 전체에는 작업자 내 기타 처리도 포함되므로 표의 구간을 더한 값과 정확히 같지 않을 수 있습니다. HTTP 응답을 끝내지 못한 경우 세부 시간은 확인할 수 없다고 표시합니다.

이 세부 구간은 Windows 함수가 반환할 때까지의 시간입니다. 순수 업로드·네트워크 왕복·Discord 내부 계산을 각각 측정한 값은 아닙니다. 이미 응답을 받았거나 1ms 미만인 호출은 0ms로 표시될 수 있습니다. 한 구간에 시간이 몰린 것만으로 서버 위치나 인터넷 회선을 원인으로 확정하지 마세요.

**UI 이벤트 전달은 실제 화면을 그린 시간이 아닙니다.** 화면 갱신·게임 프레임·모니터 표시까지 측정하지 않습니다. 번역 봇이 문장을 번역하고 답글을 올리는 시간도 포함하지 않습니다. 이 기록의 전송 완료는 **원문을 Discord가 저장했다는 확인**입니다.

## 계속 느리면 보내 줄 정보

**최근 전송 시간 창만 캡처**하고, 다음 세 가지를 함께 알려 주세요.

- **Discord 채널의 원문도 늦게 올라오는지**, 원문은 먼저 올라왔는데 **Sideglow 표시만 늦는지**, 또는 **번역 답글만 늦는지**
- 연결 직후 **첫 메시지만** 느린지, 다음 메시지들도 계속 느린지
- 체감상 몇 초 정도 기다렸는지

이 정보와 구간별 시간을 함께 보면 전송 대기, 대상 확인 요청, 실제 POST, 화면 표시, 번역 봇 처리를 구분할 수 있습니다. 시간 창에는 채팅 내용·채널 주소·웹후크·로그인 토큰이 들어 있지 않습니다. 연결 설정 파일이나 웹후크 URL을 보내 줄 필요는 없습니다.

## 전송 제한 또는 확인 실패

HTTP 429가 나오면 Discord의 전송 제한에 도달한 상태입니다. 서버가 유효한 `retry_after`를 제공한 경우 대기 시간을 초 단위로 안내합니다. [Discord Rate Limits 문서](https://docs.discord.com/developers/topics/rate-limits)는 응답의 제한 정보를 따르도록 안내합니다. 제한 값을 임의의 고정 속도로 가정하거나 POST를 자동으로 반복하지 않습니다.

네트워크 오류로 결과를 확인하지 못했다면 **이미 전송되었을 가능성이 있습니다.** Discord 채널을 먼저 확인한 뒤 다시 보내세요. 응답에서 다른 채널이 확인된 경우에도 자동 재전송하지 않고 웹후크 설정의 재확인을 요구합니다.

## 기록과 측정의 범위

시간 정보는 프로세스 메모리에 최근 한 건만 보관합니다. 채팅 본문·ID·URL·접속 정보를 시간 기록에 넣지 않으며 자동 파일 로그나 외부 보고를 만들지 않습니다. 이 기능이 별도의 메시지를 보내거나 Discord 기록을 반복 조회하지도 않습니다.

시스템 프록시 검색은 환경에 따라 시간이 걸릴 수 있습니다. [Microsoft의 자동 프록시 성능 안내](https://learn.microsoft.com/en-us/windows/win32/winhttp/autoproxy-issues-in-winhttp)는 검색 지연과 세션 캐시를 설명하고, [WinHttpOpen 문서](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpopen)는 자동 프록시 설정의 의미를 설명합니다. 이 프로그램은 지연을 줄이기 위해 시스템 프록시를 임의로 우회하지 않습니다.

실제 수행한 빌드·검사와 남은 실환경 확인은 [VALIDATION.md](VALIDATION.md), CPU·메모리 측정 방법은 [B-PERFORMANCE.md](B-PERFORMANCE.md)에 있습니다.
