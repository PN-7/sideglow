# Sideglow 0.4.0-preview.1 — B 방식과 채널 탭의 성능 비교

**이 문서는 측정 방법이며 실제 성능 결과가 아닙니다.** 개발 환경은 Linux이고 실제 Windows Discord 계정과 연결하지 않았으므로, Discord의 CPU·메모리 증가량을 아직 측정하지 못했습니다. 기존 중계 서버나 모의 연결의 수치를 B의 측정 결과로 대신하지 않습니다.

B는 실행 중인 Discord에서 선택한 채널의 이벤트를 로컬 IPC로 받고, Rust 네이티브 창에 표시합니다. 새 브라우저 엔진을 띄우거나 채널 기록을 반복 조회하지 않습니다. 실제 부담은 Discord 버전, 메시지 유입량, 화면 상태, 게임·통화 상태에 따라 달라지므로 같은 PC에서 비교합니다.

## 탭을 늘렸을 때 달라지는 것

탭은 최대 8개이며 **선택한 한 채널만 수신·번역**합니다. 프로그램은 수신·발신을 관리하는 `Client` 하나와 번역 담당 하나를 사용합니다. 비활성 탭마다 연결·번역 작업자·렌더링 창을 더 만들지 않으며, 비활성 탭을 순회하는 폴링이나 새 메시지 알림도 없습니다.

| 상태 | 유지하는 작업·데이터 |
|---|---|
| 선택한 탭 | 한 채널의 수신·발신, 최대 200개 메시지 객체, 해당 탭이 번역 ON이면 기존 번역 작업자 최대 두 개 |
| 비활성 탭 | 연결 주소와 탭 이름, 최대 40개 메시지 객체, 작성 중 글과 전송 실패 초안. 새 수신·번역 요청·알림 없음 |
| 탭 전환 | 이전 채널의 새 작업 중단, 새 채널의 연결·초기 기록 조회. 캐시된 기록은 연결 초기화 동안 표시할 수 있으나 실시간 수신된 기록을 뜻하지 않음 |

이 설계는 여러 채널을 동시에 구독할 때 생기는 추가 처리를 피합니다. 대신 비활성 탭의 짧은 기록·초안을 보관하는 메모리는 늘어납니다. 원문·답글·번역은 각각 메시지 객체로 세며, 메시지 길이도 다르므로 “탭 하나당 몇 MB”를 고정 수치로 약속하지 않습니다. 실제 CPU·메모리가 단일 탭과 같거나 차이가 없다고 측정한 결과도 없습니다.

전환 직전에 이미 제출한 통신 요청은 정리될 때까지 남을 수 있습니다. 기존 번역 작업이 끝나기 전에 새 번역 작업자를 추가로 시작하지 않으며, 이전 채널의 요청을 새 채널로 돌려 보내지 않습니다. 비활성 탭의 상시 번역 기능은 아닙니다.

## 먼저 확인할 것

실제 B 연결에서 인증과 지정 채널의 메시지 수신이 성공한 후 측정합니다. 로그인 창이 열렸거나 연결 대기 상태라는 이유만으로 B가 정상 연결됐다고 판단하지 않습니다. 아래 스크립트는 프로세스의 자원 사용량만 읽으며, Discord 권한이나 IPC 연결 성공 여부를 확인하지 않습니다.

기존 UI의 타이머는 게임 창 상태·자동 숨김·수신 큐를 확인합니다. 대기 중에 타이머가 실행된다는 이유만으로 전체 창을 다시 그리거나 Discord를 반복 조회할 필요는 없습니다. 비교 중에는 같은 창 크기, 글꼴, 숨김 옵션과 게임·통화 상태를 유지합니다.

## 실행

Windows PowerShell 5.1 이상에서 프로젝트 폴더를 열고 실행합니다. 관리자로 실행할 필요는 없습니다.

```powershell
.\scripts\measure-b.ps1 -OutputDirectory "$env:USERPROFILE\Desktop\SideglowMeasurements"
```

저장 폴더를 생략하면 스크립트가 위치를 묻습니다. 실행할 때마다 지정한 로컬 폴더 안에 고유한 결과 폴더를 만들기 때문에 이전 결과를 덮어쓰지 않습니다. 네트워크 경로와 네트워크 드라이브는 사용하지 않습니다. Windows의 실행 정책이 차단한다면 조직·PC 정책에 맞는 실행 방법을 사용합니다. 이 스크립트는 실행 정책을 변경하지 않습니다.

기본값은 **각 단계 30초, 약 1초 간격, 시작 전 안정화 5초**입니다. 단계마다 준비한 뒤 Enter를 누릅니다. 측정 직전 5초 동안 이전과 같은 게임·전경 창 상태로 돌아가세요. 각 단계의 길이를 늘리거나 평소 메시지 유입 단계까지 포함하려면 다음처럼 실행합니다.

```powershell
.\scripts\measure-b.ps1 -OutputDirectory "$env:USERPROFILE\Desktop\SideglowMeasurements" -Seconds 120 -IncludeTraffic
```

| 단계 | 준비할 상태 | 목적 |
|---|---|---|
| `baseline` | Discord 실행, 새 메시지 없음, Sideglow 완전히 종료 | Discord 자체의 기준 사용량 |
| `b_idle` | Sideglow 실행, 실제 B 연결과 초기 기록 수신 완료, 새 메시지 없음 | 연결을 유지할 때의 추가 부담 |
| `b_traffic` | `-IncludeTraffic`을 지정한 경우만 진행. B 연결을 유지하며 평소 수준의 메시지 유입 관측 | 메시지 처리·표시 중의 사용량 |

채팅 **OFF는 게임 위 표시·입력 단축키를 끄고 선택한 탭의 연결은 유지**합니다. 공용 번역 실행도 별도 토글입니다. 따라서 **기준 측정에서는 Sideglow 프로세스를 완전히 종료**합니다. 스크립트가 프로그램을 실행·종료하거나 설정을 바꾸지는 않습니다. 단계 시작 시 Discord와 Sideglow 프로세스의 존재만 확인하고 준비 상태가 맞지 않으면 다시 기다립니다. 파일 이름을 바꾸었다면 `sideglow.exe`로 되돌린 뒤 측정합니다.

`b_traffic`은 사용자가 직접 마련한 정상적인 메시지 유입을 관측합니다. 스크립트가 채팅이나 웹후크 요청을 보내지 않습니다. 로그인 정보, 접속 토큰, 웹후크 주소, 채널 내용, 앱 설정 파일도 읽지 않습니다.

가능하면 같은 Discord 버전·계정·채널, 같은 게임 장면·화면 상태, 같은 통화 상태에서 비교합니다. Discord 업데이트, 다운로드, 통화 시작·종료 등이 겹친 결과는 따로 취급합니다. 30초는 짧은 확인용입니다. 작거나 불안정한 차이를 판단하려면 더 긴 구간으로 반복하고, Discord 자체의 자연 변동과 구별해야 합니다.

### 탭 개수의 영향을 따로 비교하기

탭 수를 비교하려면 스크립트를 두 번 실행하고, 각 실행의 `b_idle` 준비 상태를 다르게 만듭니다. 첫 실행은 한 탭, 두 번째는 여러 탭을 저장한 상태로 준비하되 **같은 채널을 선택하고 같은 화면·번역 ON/OFF 상태**로 측정합니다. 스크립트는 탭 개수를 자동으로 읽거나 바꾸지 않으므로 몇 개를 사용했는지 결과 폴더와 함께 메모하세요.

단순히 탭 주소만 추가한 상태와, 각 탭을 한 번 방문해 기록이 남은 상태는 다릅니다. 보관 메모리를 확인하려면 각 탭을 방문한 뒤 원래 측정 채널로 돌아오고 연결·정리가 끝난 후 유휴 측정을 시작합니다. 탭을 바꾸는 순간의 초기 조회 비용은 별도 구간으로 살펴야 하며, 그 짧은 변화를 유휴 상태의 상시 비용으로 해석하지 않습니다.

번역 ON/OFF 비교도 별도 실행에서 같은 메시지 유입 조건을 맞춥니다. 유휴 구간만으로 실제 번역 요청 중의 CPU·메모리나 API 응답 시간을 판단할 수 없습니다. 번역 지연은 **설정 → 최근 번역 시간…**에서 따로 확인합니다.

## 결과 파일

### `samples.csv`

각 관측 구간마다 `Discord`와 `Sideglow` 행을 별도로 기록합니다. `Discord`는 이름이 `Discord*`인 모든 프로세스의 합계이며, `Sideglow`는 `sideglow` 프로세스의 합계입니다. Discord의 메인 프로세스 하나만 비교하지 않습니다. 이 이름 규칙에 해당하는 다른 프로그램이 있다면 측정 전에 확인하세요.

| 주요 열 | 뜻 |
|---|---|
| `stage`, `process_group` | 측정 단계와 프로세스 그룹 |
| `interval_seconds` | 실제 관측 간격. CPU 계산에 이 값을 사용 |
| `process_count` | 그 시점에 관측된 해당 그룹의 프로세스 수 |
| `cpu_total_capacity_percent` | 전체 논리 프로세서 용량을 100%로 환산한 CPU 사용률. 완전하게 비교할 수 없는 구간은 빈 값 |
| `cpu_sample_status` | `complete` 또는 프로세스 변경·접근 실패 등 제외 이유 |
| `private_memory_mib` | 그룹 전체의 private memory 합계. 현재 프로세스 중 읽지 못한 항목이 있으면 빈 값 |
| `added_process_identities`, `removed_process_identities` | 이전 관측과 비교해 나타나거나 사라진 프로세스 식별자 수 |
| `stage_process_presence_ok` | 기준 단계에 Discord만, B 단계에 두 앱 모두 관측됐는지 여부 |

`cpu_known_processes_percent`와 `private_memory_readable_processes_mib`는 일부 프로세스만 읽힌 경우 원인을 조사하기 위한 부분 합계입니다. 전체 사용량을 나타내는 숫자로 사용하지 않습니다.

### `summary.json`

`stages`에서 각 단계·각 앱의 평균, 최대, p95를 봅니다. `comparisons`에는 기준 단계와의 **평균 차이**가 있습니다.

| 항목 | 해석 |
|---|---|
| `cpu_total_capacity_percent.mean` | 유효 관측 구간의 시간 가중 평균 CPU 사용률 |
| `cpu_total_capacity_percent.max`, `.p95` | 관측 구간 CPU 사용률의 최대와 p95 |
| `private_memory_mib.mean`, `.max`, `.p95` | 관측 시점 private memory의 산술 평균, 최대와 p95 |
| `cpu_mean_delta_percentage_points` | 해당 단계 평균 CPU − 기준 평균 CPU. 단위는 퍼센트포인트 |
| `private_memory_mean_delta_mib` | 해당 단계 평균 private memory − 기준 평균 private memory |
| `valid_samples`, `excluded_samples` | 통계에 포함·제외한 관측 수 |
| `stage_conditions_ok` | 비교할 두 단계가 완료됐고 예상한 프로세스 상태가 유지됐는지 여부 |

예를 들어 CPU가 1.0%에서 1.2%가 됐다면 차이는 **+0.2퍼센트포인트**입니다. 이것은 설명용 숫자이며 실제 측정 결과가 아닙니다. `Discord` 차이는 기존 Discord 프로세스에 더해진 사용량을 살피는 데 사용하고, `Sideglow` 값은 새 앱 자체의 사용량으로 따로 봅니다.

`b_traffic`과 유휴 기준 단계의 차이에는 **채팅이 늘어나서 Discord 자체가 하는 일**도 포함됩니다. 이 차이를 전부 B의 추가 부담이라고 해석하지 않습니다. 메시지 처리 중 B만의 영향을 더 구체적으로 비교하려면 Sideglow가 꺼진 상태에서도 비슷한 메시지 유입량을 별도로 관측해야 합니다. JSON의 `comparison_scope`에도 이 구분을 기록합니다.

`run_complete: false`, 완료되지 않은 단계, `stage_conditions_ok: false`, 많은 제외 표본이 있는 결과는 그대로 성능 판정에 쓰지 않습니다. `stage_conditions_ok: true`도 연결 성공이나 실험 조건의 동일성을 자동으로 입증하지는 않습니다. Discord/Sideglow의 프로세스 존재와 측정 완료 여부만 확인합니다.

## 계산 방법과 한계

CPU는 프로세스의 누적 `TotalProcessorTime` 차이를 실제 경과 시간과 논리 프로세서 수로 나눕니다. 예를 들어 논리 프로세서 8개 중 하나를 지속해서 전부 사용하면 이 기준에서는 약 12.5%입니다. 논리 프로세서 수는 로컬 `Win32_ComputerSystem.NumberOfLogicalProcessors`에서 읽습니다. 조회에 실패하면 .NET 값으로 대체하고 경고 및 사용한 출처를 기록합니다. 큰 시스템이나 CPU 사용 범위가 제한된 환경에서 이 대체 경로가 사용됐다면 결과의 `logical_processors`를 확인하세요.

프로세스는 PID와 시작 시간의 조합으로 구분합니다. 새 프로세스가 생겼을 때 그 프로세스의 이전 누적 CPU 시간을 이번 1초 동안의 작업으로 잘못 더하지 않습니다. 프로세스가 사라졌거나 카운터를 읽지 못한 구간은 해당 그룹의 CPU 통계에서 제외합니다. 제외한 값을 0으로 채우지 않습니다. 다만 관측 사이에 시작되고 종료된 매우 짧은 프로세스는 잡을 수 없고, 제외 구간이 많으면 통계에 편향이 생길 수 있습니다.

이름조차 읽기 전에 사라져 어느 그룹인지 알 수 없는 프로세스가 있으면 `unclassified_process_count`에 기록하고 두 그룹의 해당 구간을 보수적으로 제외합니다. 이는 실제로 Discord와 무관한 프로세스여도 적용됩니다.

메모리는 `PrivateMemorySize64`를 합산하고 1,048,576으로 나눈 MiB입니다. 다른 프로세스와 공유할 수 없는 할당 메모리이며, 실제 물리 RAM 상주량인 Working Set, GPU 메모리, 시스템 전체 메모리 증가량과 같지 않습니다. Working Set을 단순 합산할 때 공유 페이지가 겹쳐 보이는 문제를 피하기 위해 이 지표를 사용합니다.

p95는 관측값을 정렬한 뒤 `ceil(0.95 × 유효 표본 수)`번째 값을 선택합니다. 최대값과 p95는 약 1초 간격 관측에서의 값이며 순간 CPU·메모리 최고점을 보장하지 않습니다. 평균 CPU는 구간 길이로 가중하고, 메모리는 관측 시점의 산술 평균을 사용합니다.

스크립트 자체의 실행·파일 저장 부담도 존재합니다. 두 단계에서 같은 방식으로 관측하지만, 이것만으로 원인과 결과를 엄밀하게 증명할 수는 없습니다. FPS, 프레임 시간, 입력 지연, GPU 사용량, 네트워크 사용량도 이 스크립트의 측정 범위가 아닙니다. 자원 사용량과 별개로 게임 중 입력·한글 IME·클릭 통과도 실제 Windows에서 확인해야 합니다.
